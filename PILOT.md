# Пилот DoSmart: бэкенд и сайт

## Актуальный процесс с 28.09.2026

Терминал: каталог → корзина → ФИО осуждённого, название/номер учреждения и WhatsApp родственника → согласие → «Отправить заявку в DoSmart». Приложение получает номер заявки. Чат родственника и самостоятельное оформление по коду не участвуют в этом сценарии.

Админка `/admin/orders`: новая заявка сразу видна с товарами и контактами. Фильтр «Новая заявка» показывает необработанные обращения. В карточке сотрудник открывает WhatsApp родственника, уточняет данные, согласует доставку, затем выбирает её тип и статус «Ожидает оплаты». Только после этого доступны ссылка на экран оплаты и подготовленный текст WhatsApp. Кнопка WhatsApp не отправляет сообщение автоматически. Сотрудник сам отправляет ссылку и сверяет платёж в Kaspi Pay перед статусом «Оплачен».

До согласования доставка обозначена как «Не согласована», сумма относится только к товарам. Новые заявки не удаляются через 4 дня: очистка затрагивает только черновики без заказа. Старые заказы и API сохранены. Список учреждений для нового сценария не обязателен: введённое название хранится текстом и проверяется сотрудником.

### Новый API

`POST /api/v1/terminal/orders`, Bearer текущей сессии терминала. Тело:

```json
{
  "request_id": "f04249ed-b062-44b8-9472-f9c1e0f3c36a",
  "items": [{"product_id": 1, "quantity": 2}],
  "prisoner_name": "Иванов Иван Иванович",
  "institution_name": "Учреждение №12",
  "contact_phone": "+77011234567",
  "consent": true
}
```

Ответ 201: `order_number`, `status`, `subtotal`. Цены/статусы/доставка из запроса не принимаются. ФИО и учреждение сохраняются из формы, а проверенная сессия связывает пользователя с заявкой. Повтор той же попытки возвращает тот же заказ; изменение данных или пользователя при том же UUID — 409. После потери ответа приложение блокирует изменение формы до безопасного повтора. Телефон нормализуется, включая 8XXXXXXXXXX → +7XXXXXXXXXX.

Локальная проверка 28.09.2026: 19 серверных тестов / 223 проверки, 7 Flutter-тестов; анализ модуля Flutter без замечаний.

### Выкладка на тестовый сервер

1. Сделать бэкап существующей БД. Обновить бэкенд и выполнить `php artisan migrate --force` (новая миграция `2026_09_28_000001_add_terminal_submission_hash`). Не использовать `migrate:fresh` на базе с данными.
2. Указать `APP_URL=https://ВАШ_ДОМЕН`, действующий `TERMINAL_IDENTITY_URL=https://СЕРВЕР_ТЕРМИНАЛА/api/user`, `KASPI_PAYMENT_URL` и `DOSMART_WHATSAPP`. Проверка сессии по-прежнему обязательна; без неё новый API закрыт. Обновить кэш конфигурации по процедуре выбранного окружения.
3. Собрать новую версию Flutter с `--dart-define=DOSMART_BASE_URL=https://ВАШ_ДОМЕН`. APK от 26 сентября использует старый процесс; заменить его новой сборкой. Учётные записи сотрудников создаются командой `php artisan admin:create`.
4. Проверить на тестовой сессии: обязательные поля, получение заявки в админке, повтор запроса, подготовку доставки и ссылки, ручное подтверждение оплаты. Настоящие сообщения/оплаты локальные тесты не выполняют.

## Сайт и предыдущий сценарий (сохранены для совместимости)

- Каталог → корзина → «Отправить родственнику»: создание черновика, случайный восьмизначный код, ссылка и сокращённый текст. Кнопка на сайте копирует сообщение; отправку в чат терминала подключает приложение.
- Главная `/shop`: ввод кода. `/o/{code}`: готовая корзина, ФИО, активное учреждение, WhatsApp, доставка 3000/5000 ₸, согласие. Гостевое оформление разрешено.
- Покупатели входят по телефону/паролю через `/shop/login`, сотрудники — по логину/паролю через `/admin/login`. Ссылка сотрудникам есть внизу сайта и на форме входа. Админские учётные записи создаются только командой `php artisan admin:create operator`; пароль вводится скрыто, общих паролей в проекте нет.
- Зарегистрированный покупатель видит свои новые заказы в кабинете. Гостевые заказы доступны по сохранённой ссылке, автоматически к аккаунтам не привязываются. Вход со страницы корзины возвращает к ней.
- Экран оплаты показывает сумму, номер, копирование, настраиваемую ссылку Kaspi и переход в WhatsApp. Без настроенной ссылки нет активной кнопки оплаты. Автоматической проверки Kaspi и загрузки квитанций на сервер нет.
- Сотрудник вручную подтверждает сверку платежа в Kaspi Pay, указывает ID платежа, меняет статус. Скриншот не подтверждает оплату. Из неоплаченного состояния нельзя перейти к доставке. Оплаченный заказ нельзя просто отменить: нужен возврат.
- Возврат фиксируется после его выполнения в Kaspi Pay. Поле «Возвращено всего» — накопленная сумма, от частичной до полной, не выше стоимости заказа; причина обязательна. Операция в админке сама деньги не возвращает.
- Неоформленные черновики удаляются через 4 дня ежедневным `drafts:prune`. Анонимные события воронки сохраняются отдельно: создание, оформление, подтверждение оплаты. В админке считаются только события источника `terminal` за всё время, включая позднее возвращённые оплаты. Это счётчик созданных корзин, а не подтверждённых отправок в чат.

## Предыдущий API черновиков (не используется новой сборкой терминала)

`POST /api/v1/drafts`, JSON, заголовки `Accept: application/json`, `Content-Type: application/json`, `Authorization: Bearer <TERMINAL_API_TOKEN>`.

```json
{
  "request_id": "f04249ed-b062-44b8-9472-f9c1e0f3c36a",
  "items": [{"product_id": 1, "quantity": 2}],
  "prisoner_name": "ФИО, если известно",
  "institution_id": 1
}
```

Последние два поля необязательны. До 100 уникальных позиций, количество 1–1000. Цены и суммы от клиента игнорируются. Справочники: `GET /api/v1/products`, `GET /api/v1/institutions`.

```json
{
  "code": "7K3M9A2B",
  "url": "https://dosmart.kz/o/7K3M9A2B",
  "expires_at": "2026-09-30T12:00:00+00:00",
  "subtotal": 700,
  "chat_text": "Корзина DoSmart…"
}
```

Код состоит из 8 случайных символов без неоднозначных I/O/0/1. В сообщение попадают первые 8 позиций, остальные сокращаются. URL строится по `APP_URL`, поэтому на сервере необходимо указать правильный HTTPS-домен.

Один `request_id` (UUID) на одну отправку; при сетевом сбое повторять тот же запрос с тем же ID. При изменении корзины или новой отправке генерировать новый UUID. Повторный запрос не создаёт второй черновик. Ответы: 201 — готово; 401 — токен неверен или не настроен; 409 — ID использован с другой корзиной; 410 — черновик истёк; 422 — ошибка товаров/полей; 429 — ограничение частоты, повторить позже. Токен не помещать в URL, сообщения чата или публичный JS; интеграцию делать через доверенный сервер терминала.

Приложение должно отправить `chat_text` существующим механизмом чата. Проверку кликабельности и модерации можно завершить только после доступа к приложению. В этой поставке приложение родственника не менялось.

## Правила оформления

Сервер повторно проверяет наличие и цены. Если цена изменилась после открытия формы, оформление отклоняется с просьбой обновить страницу. Доставку сервер выбирает по `delivery_type`, а не по сумме от клиента. Повторная отправка формы возвращает уже созданный заказ; черновик блокируется транзакцией при оформлении.

Код — доступ к корзине, его нельзя публиковать. После оформления по ссылке доступны только сумма, номер и статус: ФИО и WhatsApp на экране оплаты не раскрываются. Маршруты ограничены по частоте, страницы помечены no-store/noindex и не передают Referer. В локальном просмотре ссылки приватности и оплаты не требуют внешних сервисов.

Устаревшие `POST /api/v1/orders` и `POST /shop/orders` возвращают 410: обходить новый поток оформления без согласия нельзя. `GET /api/v1/orders/{number}` требует сессию покупателя и возвращает только его заказ. Существующие мобильные клиенты нужно перевести на `/api/v1/drafts`.

## Запуск на сервере

В проекте два Compose-файла. `docker-compose.production.yml` — самостоятельный, не накладывать его на dev-файл. Производственная база не публикует порт; наружу открыты только 80/443 Caddy. Все сервисы перезапускаются после сбоя. Docker должен автоматически запускаться при старте сервера.

1. Настроить DNS `dosmart.kz` на сервер, открыть 80/443, проверить IPv6-запись, если она есть.
2. Скопировать `.env.production.example` в `.env.production`, заполнить `APP_KEY`, уникальные `DB_PASSWORD`, `TERMINAL_API_TOKEN` (не менее 32 случайных символов), `KASPI_PAYMENT_URL` (реальная HTTPS-ссылка удалённой оплаты), `DOSMART_WHATSAPP` (номер с кодом страны). Не коммитить этот файл.
3. `APP_KEY` можно сгенерировать локально командой `php artisan key:generate --show`; случайный токен — `openssl rand -hex 32`. Ключ существующего приложения не заменять при обновлении.
4. Проверить реквизиты и согласовать текст обработки данных в `resources/views/shop/privacy.blade.php` с владельцем: это базовый текст пилота, сведения об операторе и его сроках хранения должны быть утверждены до реальных заказов.
5. Выполнить из корня проекта:

```sh
docker compose --env-file .env.production -f docker-compose.production.yml build
docker compose --env-file .env.production -f docker-compose.production.yml up -d postgres
docker compose --env-file .env.production -f docker-compose.production.yml run --rm app php artisan migrate --force
docker compose --env-file .env.production -f docker-compose.production.yml run --rm app php artisan admin:create operator
docker compose --env-file .env.production -f docker-compose.production.yml up -d
```

При обновлении существующей базы сначала сделать резервную копию. Демонстрационные сидеры в рабочую базу не запускать. Категории, учреждения и товары должны быть заполнены реальными данными. Фото сохраняются в отдельном томе `uploads`.

Caddy получит сертификат при доступном домене и открытых портах; это не означает, что сертификат уже выпущен в локальной среде. Проверить `/up`, вход, формы, HTTPS-переадресацию и журнал:

```sh
docker compose --env-file .env.production -f docker-compose.production.yml logs --tail=100 app scheduler web backup
```

Логи приложения отправляются в stderr, Docker ограничивает размер файлов. Веб-доступ-логи с кодами заказов не включены.

## Бэкап и восстановление

Сервис `backup` делает `pg_dump -Fc` при старте и каждые 24 часа, проверяет читаемость архива и сохраняет в `backups/` с доступом только владельцу. Хранятся 14 дней. Ошибка видна в `docker compose logs backup`; автоматических внешних уведомлений пока нет. Скопировать резервные копии и том фото на отдельный защищённый носитель/сервер: копия рядом с базой не переживёт потерю всего сервера.

Ручной бэкап:

```sh
docker compose --env-file .env.production -f docker-compose.production.yml exec backup sh /backup.sh
```

Проверка восстановления выполняется в отдельную пустую тестовую базу, не поверх рабочей:

```sh
docker compose --env-file .env.production -f docker-compose.production.yml exec postgres createdb -U dosmart restore_check
docker compose --env-file .env.production -f docker-compose.production.yml exec -T postgres pg_restore -U dosmart -d restore_check --no-owner < backups/ИМЯ.dump
```

Указать фактическое имя пользователя БД, если оно отличается. Проверить таблицы, заказы, количество записей. После проверки удалить только созданную тестовую базу. Отдельно хранить `.env.production` и ключ шифрования безопасным способом.

## Приёмка перед запуском

- Код открывается вручную и по ссылке, корзина совпадает, срочная доставка прибавляет 5000 ₸, обычная 3000 ₸.
- Чужой покупатель не получает доступ к заказам аккаунта/админке; сотрудник входит по логину.
- Реальная ссылка проходит модерацию и кликается в чате терминала.
- Владелец проводит 1–2 настоящие оплаты: сверяет их в Kaspi Pay, отвечает «Принято», фиксирует доставку; отдельно проверяет возврат.
- Назначен ответственный за WhatsApp, платежи и статусы, записан контакт на случай сбоя.
- Проверены восстановление бэкапа, автоматический старт Docker и ежедневная очистка черновиков.

Реальные платежи, развёртывание на домене и интеграция чата не выполнялись локально. Шаблон журнала фидбэка — `docs/pilot-feedback.md`.

## Проверка сессий Flutter-терминала и прежние черновики

Модуль реализован в соседнем `flutter-internal`, ветка `codex/dosmart-terminal-shop`; инструкция сборки и ограничения — в его README.md. Приложение использует существующие контакты и отправку текста, приложение родственника менять не требуется.

Установить `TERMINAL_IDENTITY_URL` на доверенный HTTPS endpoint существующего `/api/user`. По Bearer-токену он должен возвращать плоский профиль (`id`, `id_number`, ФИО, `establishment.id`). Адрес задаёт только оператор сервера, приложение его передать не может; редиректы запрещены. До настройки endpoint создания мобильного черновика закрыт (503). Для сопоставления учреждений задать `TERMINAL_INSTITUTION_MAP` как JSON-объект внешних ID к ID учреждений магазина. Несопоставленное учреждение выбирает родственник.

- `POST /api/v1/terminal/drafts` — текущий Bearer-токен приложения; `request_id` UUID, `items` с `product_id` и `quantity`. Сервер получает ФИО/учреждение из проверенного профиля, считает цены и привязывает повтор запроса к пользователю.
- `POST /api/v1/terminal/drafts/{code}/sent` — тот же Bearer, фиксирует успешный ответ API чата; повтор безопасен, чужой код недоступен. Метрика «Принято чатом» может недосчитаться при сбое подтверждения и не означает прочтение.
- Старый `/api/v1/drafts` с серверным ключом сохранён для доверенной интеграции. Этот ключ не встраивать в APK.

Дополнительные тесты интеграции: подмена ФИО/учреждения, повтор UUID, изоляция пользователей, повтор подтверждения чата и закрытый доступ при ненастроенной/истёкшей сессии. Итого на SQLite: 14 тестов, 145 проверок. Настоящая отправка сообщений и рабочий сервер в этой проверке не задействованы.
